## Measurement assessment

The private worker opens its native outer CUDA window after imports and closes it after CLI/export/assertion work. Owning `hardware/memory.py:78-125` folds nested allocator peaks into every open window before resetting counters. Thus the outer measurements remain meaningful despite nested window resets. They exclude pre-window import allocations that were already freed, CUDA context/driver/non-PyTorch allocations and other processes. Host `peak_wset` covers process lifetime; final RSS is not a host peak. Launcher timing includes imports/startup and differs appropriately from worker stage time.

Actual stage JSON confirms calibration39.619s worker /58.395s launch, peak allocated/reserved2,612,107,776/2,925,527,040 bytes and host peak14,241,726,464 bytes; sparse68.081s /84.134s,2,576,283,136/2,889,875,456 bytes and host peak14,242,959,360 bytes. These agree with the phase reports. Sparse's4,772MiB sampled global GPU reading is explicitly separate from the process allocator window and is not certified as the true global maximum. Caching/CPU-only phases likewise retain distinct scopes. The256-area data and substantial host offload preclude extrapolation to4GB/6GB operation, higher resolution, or equivalent throughput/quality.
