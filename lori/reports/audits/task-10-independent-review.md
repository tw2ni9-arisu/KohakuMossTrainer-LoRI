## 1. 边界与方法

**复核边界**

- 只读：所有写入仅限 `experiment/task10/review-phase-a.json` 与本文件。
- CPU only：`CUDA_VISIBLE_DEVICES=''` 全程设置；`torch.load` 一律 `map_location='cpu'`；未调用任何 GPU、未训练、未出图。
- 未修改任何实验产物；未 `git commit`；未改动 `KohakuMossTrainer/` 源码。
- 与「对照/出图」作业并发运行：其日志与产物在复核期间继续变化，因此本文件的协议结论**绑定**于 §2.7 表里记录的 `compare.py / config.py / resolved.json / freeze.json` sha256。

**方法要点（为什么这些数字可以互相信）**

1. **独立重算，不转述**。条数用自己切分字节流统计；哈希用自己实现的 `sha256('<dtype>:<shape>:' + 原始字节)`；组合摘要按 `worker.py:695` 的定义复现（先 A 段、再 alpha 段）。
2. **SQLite 只读且零副作用**：`file:<path>?mode=ro&immutable=1` + `PRAGMA query_only=1`。先在副本上做了对照实验证明 `immutable` 不产生 `-wal/-shm` 而 `mode=ro` 会，再对三个 db 读前/读后重算 sha256（三次都等于 freeze 记录值）。
3. **safetensors 独立读取**：`safe_open` 在 `with` 块内 `clone()` 后自算 digest（教训见 ISS-05：块外使用 mmap 张量会产生假阴性，我第一轮就踩到，纠正后 252/252 命中）。
4. **参数化验证**：报告里的每个关键数字都要在产物里找到对应字段，然后**重新计算**；找不到对应证据的一律记「无法核对」，不为「通过」而调整口径。

## 3. 发现的问题（6 条，均有证据与复算值）

### ISS-01（info，但涉及「不改产物」约束）复核期间 cache 目录新增 6 个 SQLite sidecar

- 现象：`catalog/latents/text` 三个 db 各自出现 `-wal`（**0 字节**）与 `-shm`（32,768 字节），创建时间 18:02:34，最后写 18:02:46–18:03:18。
- 归因：我先做了对照实验——在副本上用 `?mode=ro&immutable=1` 打开**不产生** sidecar，用 `?mode=ro` 打开**会**产生。我的所有读法都是 immutable，因此这 6 个文件来自**同一窗口内的另一个非 immutable 读取方**（并发的审计子代理或对照作业的预检）。
- 影响：**零内容改动**——三个 db 的 sha256 与 `freeze.json` 完全一致（`fd4bd5de…` / `4cb07744…` / `180f536b…`）；0 字节 WAL 表示没有待回放的提交帧。
- 处置建议：等出图与所有读方结束后删除这 6 个文件即可完全恢复 freeze 状态；不要现在删（有进程可能仍持有句柄）。

### ISS-02（info）`initial-hashes.json` 的组合摘要文案与实际排序不符

文案写「combined: … in sorted name order」，实际 `worker.py:815` 是 `combined_digest(a_items + alpha_items)`。我用两种拼接分别计算：

- 全局 sorted → `5ae854e73e7c3e5f5d9a29eee00f57d61074da7868a918423fbc2c3dcf44d0e9`（≠记录值）
- 分块（A 段 + alpha 段）→ `3731500a5202c3068d1a8a749204c9955b52f091b0fee6139042243aaa6da108`（=记录值）

记录值正确、行为可复现，错的只是文案。建议下轮把 `digest_algorithm` 改成「先按 A 名排序、再按 alpha 名排序」的准确描述。

### ISS-03（info）运行级导出与检查点导出 sha256 不同，但张量完全相同

`lycoris`：`b7f5eb34…`（运行级）对 `c4309ca6…`（step900 内）；`comfy`：`477768fa…` 对 `c8e45d41…`。我逐张量比较得到 **756/756 与 504/504 完全相等**，元数据字典也相等，差异只在 safetensors 头部（键序/JSON 序列化）。报告 §4 只说「字节不同」，容易被读成权重有差异。

### ISS-04（low）comfy 的 fused qkv 依赖「alpha = 秩、scale = 1」的生态约定

`fused.py` 把每个子层的 `alpha/rank = 2` 折进 `up`，再把 fused `alpha` 设为 rank(24)、`up` 为 `blockdiag(2·B)`，我逐模块重构命中。但一旦某个消费端按 `dim = 24` 与 `alpha = 24` 计算 `scale = 24/24 = 1`，效果正确；若它把 `ss_network_dim = 8` 与 per-module `alpha = 24` 组合，就会得到 3 倍强度。属生态约定问题，非本轮产物缺陷，且本轮视觉评估用的是 `lycoris` 导出。

### ISS-05（info）复核方法论教训：`safe_open` 关闭后使用张量会得到假阴性

第一轮我在 `with safe_open(...)` 块内取张量、出块后计算 digest，结果 A 的 252 个张量全部不匹配，看起来像「A 被训练改动了」。改为块内 `clone()` 后全部 252/252 命中，且与 `torch.equal` 一致。**这不是产物缺陷，但足以让复核者得出相反结论**，记录在此以免后人重犯。

### ISS-06（info）「未删除任何检查点或导出」无法从终态反证

`KEEP_LAST = 4` + `SAVE_EVERY = 285` 只能证明终态恰有 4 个 step 目录；是否曾删除过中间的检查点没有历史记录可查，只能信任 stage 日志与 launch 配置。该断言应标注为「据配置与日志，非独立可证」。

### 7.7 最终裁决

**（1）训练完整性：达标。** 沿用第一阶段结论（900/900 步、4 检查点、252 entry 优化器与 21,331,968 个矩元素、A/alpha 504/504 不变、冻结全部成立），第二阶段没有出现任何反证；本次出图与审计的 stage 记录、导出哈希、初始哈希也继续与第一阶段一致。

**（2）视觉信号：未达到方案第 73 行的门槛。** 方案要求「按盲评表比较、大多数场景与两个种子下风格评分方向一致，且提示遵循与结构质量没有重复退化」。逐条对照：

- `方向一致`：以像素偏移衡量，900 更远在 21/24 行成立，但这是**幅度**不是**风格评分**；本轮**没有任何真人盲评数据**，我只有自己的观察，不能替代评分。这一条既不能算通过，也不能算不通过，只能算**未测量**。
- `没有重复退化`：**不成立**。G1（r00、r01）与 G4（r12–r15）在 900 列出现可重复的面部（细缝/无瞳眼）与手部（手掌融合成片、布偶分离的双手套）退化，占 24 行中的 6 行，且集中在两个场景而非个别样本。

因此我的裁定是：**『step 900 施加了更强、更整体化的画风先验』这一描述性结论成立；『小样本视觉增益』这一门槛结论不成立。** 依据是「强度 ≠ 质量」+「结构退化可重复」+「无盲评数据」三条同时成立。要把它降级为可发表的结论，需要按 §7.8 补 4 列轨迹与真正的盲评。

**（3）过拟合边界：无法判定，只能给出边界。** 285 张全部入训、900 步 = 3.158 轮；分段 loss 平坦（0.7128 → 0.6971 → 0.7049），而 B 的全局 L2 从 5.4967 涨到 9.7500（+77%）。参数容量在增长、训练集 loss 没有对应改善，这在没有留出集的情况下**既可能是记住训练样本、也可能是学到画风**，两者不可分。视觉上 285 步（1 轮）已经有明显改写、900 步（3.16 轮）更强但结构代价更大，这本身就是「更久不等于更好」的弱证据。

### 7.8 下一步建议（按性价比排序）

1. **四列轨迹 285 / 570 / 855 / 900**：磁盘上 570、855 的导出已经存在，只多出 ~24 张/列（生成时约 24 分钟/列），却能判断「是否单调」「855 是否已稳定」「结构退化从哪一步开始」。这是最便宜、信息量最大的一步。
2. **真正的盲评**：预注册 1–5 分量表与阈值（例如 ≥10/12 配对方向一致），第二评者、报告评分者一致率；盲评 key 与带名网格移出 run 目录，评分完成前不产出逐列哈希。
3. **同预算稀疏 LoRI 900 步**：同一 285 图、同一配方、sparsity 0.9，才能回答「稀疏是否在同预算下保住画质」——这是 LoRI 的主要论点，本轮只证明了稠密能跑。
4. **普通 LoRA 同预算基线**（rank 8 / alpha 16 / 同数据同步数）：没有它就无法区分「LoRI 的特性」与「低秩适配的共性」。
5. **独立留出集**：固定 10–15% 训练目录外的图像重训，或引入训练目录外的参考图做定性参照；这是唯一能把「学会」与「记住」分开的办法。
6. **触发词受控实验**：`TEXT_DROP > 0` 或专门构造有/无触发词的 caption 集，让 RSK-01 变成可证伪命题；像素侧同时给出 δ_adapter − δ_base。
7. **护栏**：加一列「无 adapter」canary（断言与第 1 列逐字节相等，补 RSK-08）；加一组 256² 复现（补 RSK-07）；报告里把「雨夜组更干净」限定为场景层面、剔除面部判断。

## 10. A 冻结审计（Task 12，2026-11-19）

> 用户质疑「dense 900 是否真是 LoRI、训练中 A 是否冻结」。本节只做取证摘要；完整证据在 [a-frozen-audit.md](a-frozen-audit.md) 与 [a-frozen-audit.json](../../../experiment/task12-audit/a-frozen-audit.json)。

**结论一：A 确实冻结，且是构造性冻结。** `A`/`alpha` 是 `register_buffer`（`adapters/kinds/lori.py:47-48`），只出现在 `named_buffers()`；`trainable_params()` 只枚举 `named_parameters()` 且要求 `requires_grad`（`adapters/train/adapter_set.py:246-262`），优化器只从该枚举建组（`training/build/loop.py:173-202`、`training/entry.py:300`）。因此「训练不会更新 A」不是断言或约定，而是数据结构上不可能。

**结论二：24 个检查点/掩码文件的 A 逐张量相同。** 覆盖 task6 step12/32、task8 step232、task9 dense232、task10 dense 285/570/855/900、task11 calibration 285 + sparse90/60/30 × 4 步 + 3 份掩码：A 组合摘要 **24/24** 为 `7f8b433f…`、alpha **24/24** 为 `930ce824…`、B 摘要 **24/24** 互不相同。

**结论三：优化器里没有 A。** 四份 `optim.pt`（dense 900 + 三档稀疏 900）各 252 entry，矩元素分别 21,331,968 / 2,133,198 / 8,532,788 / 14,932,378（恰为 2×B），**没有任何 state 张量是 `[8, in]` 的 A 形状**，`master` 与同 step 的 B 摘要多重集完全相等。

**结论四：受控 2 步运行时复核通过。** dense 与 sparse90 各跑 2 步（GPU）：A/alpha 252+252 全部 `requires_grad=False`、不是 Parameter、不在可训练集合、不在优化器参数组；A 的字节/版本号/摘要训练前后不变、grad hook 零命中；B 的 252 层全部收到梯度且字节改变；`optim.pt` 252 entry、矩元素与预期一致。

**结论五：导出文件没有编码「A 冻结」。** comfy 导出把 A 映射成 `lora_down.weight`、`dense_b()` 映射成 `lora_up.weight`（`lori.py:104-110`），我实测通用 lycoris 加载路径得到 `LoConModule`，`lora_down`/`lora_up` **都是 `nn.Parameter(requires_grad=True)`**——该文件可以被当普通 LoRA 继续训练并把 A 一起训掉；稀疏 comfy 导出还把 mask 展开成同尺寸稠密 B（49,601,320 B，与 dense 同大小），稀疏性不可见。原生 lycoris 文件读回全是普通 `Tensor`，通用加载器的算法匹配返回 `None`（私有格式），只有训练器的 `lori_layer_init → LoRIModule` 才把 A 装成 buffer。

**结论六：dense 900 不是论文意义的 LoRI。** 它是固定 A 的稠密 B 校准训练（`phase=calibration`、`sparsity=0.0`、全量 AdamW 状态），对应论文 `s=0` 的 LoRA-FA 极限；只有 `phase=sparse` 的三档（`active_indices` + `b_values` + 紧凑优化器状态）具备 LoRI 的定义性机制。建议的措辞修正清单见 a-frozen-audit 第 6 节（涉及 task-10 的两份对照报告、数据准备报告第 3/218 行，以及本文件标题）。

**附注（审计期间发现，非我改动）**：训练器工作树存在未提交的导出/检查点元数据补丁（8 文件 +139/−4，另有未跟踪测试），新增 `kohakumoss_lori_phase/mechanism/trainable/a=frozen_buffer/a_sha256`、`kohakumoss_container`、`kohakumoss_lori_comfy=inference_only_dense_b` 及稀疏 comfy 导出的警告。该补丁**不在任何已交付产物中**（四个导出文件的 metadata 均缺这些键），也不触碰 A 的 buffer 注册；交付文件需重新导出后才会带上这些事实。

**「原生训练 + 512² 采样导致弱于 256² 训练」——方向上成立，但不能归因于尺度不匹配。** 成立的部分：在 512² 采样下，原生 90% 稀疏的 vs-Base 幅度（26.07）明显小于 256² 稠密 900 参考（33.60），且两者距离仍有 ~28。不能归因的部分：本轮**没有对照臂**——没有「原生训练 @ 原生分辨率采样」，也没有「512² 训练 @ 512² 采样」；同时训练数据分辨率、loss 尺度（0.375 vs 0.705）、采样分辨率、掩码来源（来自 256² 校准）四重混杂。因此只能说「在 512² 采样下效果更温和、结构更干净」，不能说「是尺度不匹配造成的」。
